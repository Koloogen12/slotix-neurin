# Slotix — спека для бэкенд-разработчика

Готовый фронтенд (Design Components, `*.dc.html`) — визуальный и поведенческий референс,
все данные в нём захардкожены. Эта спека описывает, что должен делать бэкенд, чтобы фронт
стал реальным продуктом.

## 1. Что такое Slotix

Сервис онлайн-записи на встречи (аналог Calendly/Qlick). Специалист настраивает форматы
встреч и расписание, получает публичную ссылку `slotix.ru/{slug}`; клиент открывает ссылку,
выбирает слот и бронирует встречу, указав email. Пакет: лендинг → регистрация → онбординг →
кабинет специалиста → публичная страница брони → email-уведомления.

## 2. Роли

- **Владелец (специалист)** — авторизованный пользователь, управляет форматами, расписанием,
  интеграциями, тарифом. Один владелец = один аккаунт = одна публичная страница (`slug`).
  Командные страницы — фича тарифа «Про», в v1 не проектируем API под неё, только резервируем поле `plan`.
- **Клиент** — не авторизован. Идентифицируется email при брони. Никакого аккаунта/пароля у клиента нет.

## 3. Экраны фронта → что нужно от бэкенда

| Файл | Экран | Нужен бэкенд для |
|---|---|---|
| `Slotix - Лендинг.dc.html` | Маркетинг + вход/регистрация | форма email → создание аккаунта, вход (модалка) |
| `Slotix - Онбординг.dc.html` | Первичная настройка | проверка доступности slug, сохранение профиля, Google OAuth |
| `Slotix - Кабинет.dc.html` + секции | Рабочее место | CRUD форматов/расписания/интеграций/биллинга |
| `Slotix - Страница брони.dc.html`, `...Мобильная бронь` | Публичная запись | доступные слоты, создание брони, оплата |
| `Slotix - Публичные экраны.dc.html` | Состояния публичной ссылки (профиль/отмена/перенос/закрыто/404) | публичный API по брони+токену |
| `Slotix - Письма.dc.html` | 8 типов писем | транзакционные письма (см. §8) |

## 4. Модель данных (PostgreSQL)

```
users
  id, email, password_hash (nullable — если только Google/passwordless), name,
  slug (unique), timezone, avatar_url, plan ('free'|'standard'|'pro'),
  google_account_connected (bool), created_at

formats
  id, user_id, name, type ('one'|'group'|'many'), duration_min, seats (nullable, для group),
  color, provider ('meet'|'zoom'|'telemost'), price_kopecks (0 = бесплатно),
  manual_confirm (bool), status ('draft'|'live'), created_at

availability_rules
  id, user_id, weekday (0-6), start_time, end_time, timezone
  -- недельная сетка расписания; исключения — отдельно:
availability_exceptions
  id, user_id, date, is_available (bool), start_time, end_time (nullable если выходной)

calendar_connections
  id, user_id, provider ('google'), access_token, refresh_token, expires_at,
  calendar_id, busy_sync_enabled (bool)   -- список подключённых календарей и "учитывать занятость" (busy)

integration_connections
  id, user_id, provider ('google_meet'|'zoom'|'telemost'|'yookassa'),
  status ('on'|'off'|'error'), access_token, refresh_token, meta (jsonb)

bookings
  id, format_id, user_id, client_name, client_email, client_comment,
  start_at (timestamptz), end_at, client_timezone, owner_timezone_at_booking,
  status ('pending'|'confirmed'|'cancelled'|'moved'),
  channel_link (url, если video), calendar_event_id,
  cancel_reason, rescheduled_from_id (self-ref), created_at

payments
  id, booking_id (nullable — тоже подписка), user_id, kind ('booking'|'subscription'),
  amount_kopecks, status ('paid'|'pending'|'refunded'|'failed'),
  provider ('yookassa'|'mock'), provider_payment_id, receipt_url, created_at

subscriptions
  id, user_id, plan, status ('active'|'canceled'), current_period_end, created_at

auth_tokens
  id, user_id (nullable до подтверждения), kind ('magic_link'|'reset_password'|'email_code'),
  token_hash, code (6 знаков, для email-входа), expires_at, used_at
```

Примечания:
- `bookings.owner_timezone_at_booking` нужен, т.к. кабинет показывает время и в зоне клиента,
  и в зоне владельца (`time` / `timeClient` в макете «Встречи») — не пересчитывать post-factum,
  если владелец сменит таймзону.
- `formats.manual_confirm` — если `true`, бронь создаётся в статусе `pending` и ждёт
  подтверждения владельцем (кнопки «Подтвердить/Отклонить» в письме и в кабинете);
  если `false` — бронь сразу `confirmed`.

## 5. Аутентификация (все три способа — подтверждено)

1. **Email + пароль** — обычный вход, `bcrypt`/`argon2` хэш. Восстановление пароля —
   письмо со ссылкой (`reset_password` токен, TTL 30–60 мин).
2. **Google OAuth** — вход/регистрация. Тот же провайдер также используется отдельно
   для подключения календаря (§7) — два разных скоупа/потока, не путать: вход через Google
   может не давать доступ к календарю, если пользователь не согласился на этот scope.
3. **Passwordless (код на почту)** — письмо «Вход по ссылке»: кнопка-ссылка с одноразовым
   токеном ИЛИ 6-значный код, TTL 15 мин (см. `Slotix - Письма.dc.html`, тип `magic`).
   Это основной путь для email-регистрации на лендинге.

Сессия — JWT или httpOnly-сессионная кука, TTL как для типового SaaS (например, 30 дней
с refresh). Публичные эндпоинты страницы брони не требуют авторизации вообще.

## 6. Онбординг

- `GET /api/slug-availability?slug=...` — live-проверка при вводе (реализовать debounce
  на фронте, бэкенд просто проверяет уникальность + запрещённые слова, напр. `admin`, `slotix`).
- `POST /api/onboarding` — сохраняет `name`, `slug`, `timezone`, `avatar`.
- Шаг 2 (Google) переиспользует OAuth-флоу из §7.

## 7. Форматы и расписание (кабинет)

CRUD по сущности `formats` — создание/дублирование/публикация(draft→live)/удаление
как в `Slotix - Кабинет.dc.html` (`fmts()`, `setFmts`). Дублирование — копия с новым `id`,
статус всегда `draft`.

`FormatEditor.dc.html` — форма редактирования одного формата: тип (одна встреча/групповая/
несколько слотов), длительность (15–180 мин), цвет, платно/бесплатно + цена, ручное
подтверждение (`manual_confirm`), недельная доступность (превью — реальная сетка берётся
из `availability_rules`, не из формата: расписание общее для владельца, а не per-формат,
если продукт не решит иначе — уточнить при реализации, если понадобится расписание per-формат).

`CalendarsSection.dc.html` — список подключённых Google-календарей с тумблером «учитывать
занятость» (`busy_sync_enabled` per calendar_connections row) + выбор календаря для записи
новых событий (`write`).

Эндпоинты:
```
GET/POST/PATCH/DELETE /api/formats
POST /api/formats/:id/duplicate
POST /api/formats/:id/publish
GET/PUT  /api/availability            (недельная сетка + исключения)
GET      /api/calendars               (список подключений Google, busy-флаги)
PATCH    /api/calendars/:id
```

## 8. Публичная бронь — ключевая логика

Флоу (`Slotix - Страница брони.dc.html`): выбор даты/времени → форма (имя/email/коммент) →
оплата (если платно) → «Вы записаны».

1. `GET /api/public/:slug` — профиль + список опубликованных (`live`) форматов.
2. `GET /api/public/:slug/:formatId/slots?date=YYYY-MM-DD` — доступные слоты:
   пересечение `availability_rules`/`availability_exceptions` владельца минус занятые
   интервалы из подключённых Google-календарей (`busy_sync_enabled=true`) минус уже
   существующие `bookings` (`confirmed`/`pending`) минус буфер между встречами.
   **Конкурентность:** слот должен блокироваться атомарно на момент создания брони
   (транзакция + уникальный констрейнт на `(user_id, start_at)` либо advisory lock),
   иначе два клиента заберут один слот одновременно.
3. `POST /api/public/:slug/:formatId/book` — создаёт `booking`:
   - если формат бесплатный и `manual_confirm=false` → `confirmed` сразу, письмо «Вы записаны».
   - если `manual_confirm=true` → `pending`, клиенту письмо «Запрос отправлен», владельцу
     письмо «Владельцу: новая» с кнопками Подтвердить/Отклонить (см. §10).
   - если формат платный → создаётся `payment` (см. §9), бронь `pending` до оплаты,
     подтверждается вебхуком.
   - при подтверждении: создать событие в Google Calendar владельца (если подключён) +
     сгенерировать ссылку на встречу через выбранный провайдер (§9 video).
4. Отмена/перенос по ссылке из письма — публичные эндпоинты по одноразовому токену брони
   (не требуют логина клиента):
   ```
   GET  /api/public/booking/:token          — детали брони (для экрана "профиль/отмена/перенос")
   POST /api/public/booking/:token/cancel   — с причиной
   POST /api/public/booking/:token/reschedule  — новый слот, статус → 'moved'
   ```
5. Публичные состояния (`Slotix - Публичные экраны.dc.html`): профиль/отменено/перенесено/
   закрыто (владелец приостановил приём)/404 (slug не найден) — всё выводится из ответов
   выше плюс `users.accepting_bookings` (bool, добавить в таблицу `users`) для состояния «закрыто».

## 9. Интеграции

**Видео** (`IntegrationsSection.dc.html`): Google Meet, Zoom, Яндекс Телемост — все три
в объёме v1 (подтверждено). Каждая — стандартный OAuth-коннект per владелец, хранится в
`integration_connections`. При создании встречи с этой локацией — вызов API провайдера для
создания конференции, ссылка пишется в `bookings.channel_link`. Google Meet может переиспользовать
тот же Google OAuth, что и календарь, но это разные scope (`calendar` vs `meetings`/`calendar.events`)
— не завязывать один токен на оба назначения без явного запроса нужных scope.

**Календарь** (`CalendarsSection.dc.html`): Google Calendar, чтение занятости + запись
события (подтверждено). OAuth Google Calendar API, refresh-токен хранится сервер-сайд,
периодический или webhook (`watch` API) ресинк занятости.

**Оплата** (`IntegrationsSection.dc.html`, `BillingSection.dc.html`): ЮKassa —
**в v1 заглушка/мок** (подтверждено), интерфейс платежей проектируем под реальный провайдер
заранее, чтобы подключить его без переделки схемы:
- `payments` таблица и статусы уже рассчитаны на реальный вебхук-флоу.
- Мок-режим: `POST /api/payments/mock/:id/complete` эмулирует успешную оплату для тестов/демо.
- Реальный флоу (когда будет подключён): `POST /api/webhooks/yookassa` — проверка подписи,
  обновление `payments.status`, генерация чека (PDF), запись `receipt_url`.

Общий эндпоинт статуса интеграций:
```
GET   /api/integrations
PATCH /api/integrations/:provider    (on/off/reconnect)
```
Состояние `error` в макете (пример: ЮKassa) — интеграция была подключена, но токен истёк/
провайдер вернул ошибку; бэкенд должен различать `off` (никогда не подключали) и `error`
(нужна повторная авторизация).

## 10. Уведомления

8 типов писем (`Slotix - Письма.dc.html`) — все транзакционные, инициируются событиями бэкенда:

| # | Письмо | Триггер |
|---|---|---|
| 1 | Вы записаны | `booking.confirmed` (сразу или после оплаты) |
| 2 | Вход по ссылке | запрос passwordless-входа |
| 3 | Запрос отправлен | `booking.pending` (manual_confirm) |
| 4 | Владельцу: новая | `booking.pending` создана — письмо владельцу с Confirm/Reject-ссылками |
| 5 | Оплата (чек) | `payment.paid` |
| 6 | Перенос | `booking.moved` |
| 7 | Отмена | `booking.cancelled` |
| 8 | Напоминание | cron: за 1 час до `start_at` для `confirmed` броней |

Нужен транзакционный email-провайдer (например SMTP/Postmark/Unisender — на усмотрение
инфраструктуры) + шаблонизатор, верстка — плотные email-safe таблицы (без `backdrop-filter`,
см. дизайн-гайд), фронт уже даёт готовую разметку как референс.

## 11. Отдельный этап (Stage 2) — фичи с лендинга, которых нет в экранах кабинета

Подтверждено включить в спеку как отдельный этап после MVP (в текущих `.dc.html` кабинета
логики для них нет — фронт под них ещё не спроектирован, только маркетинговые обещания
на лендинге):

1. **Петля пересозвона** — авто-предложение записаться на повторную встречу через N недель
   после прошедшей (лендинг: «Созвониться через 2 недели» → «Записаться»). Нужно: поле
   `bookings.follow_up_offer_weeks` (nullable, задаётся при создании формата или брони),
   cron-джоба, письмо с предзаполненной ссылкой брони на тот же формат.
2. **Telegram-напоминания** — альтернатива/дополнение к email-напоминанию (§10, п.8).
   Нужно: Telegram-бот, привязка `chat_id` к клиенту (по email или через deep-link при
   бронировании), тот же cron, что и email-напоминание.
3. **Пакеты встреч** — специалист продаёт N встреч одним платежом (лендинг: «Продавайте
   встречи сразу пакетом»). Нужно: сущность `packages` (formats × count × price),
   `package_purchases` (клиент, остаток встреч), при брони — списание из пакета вместо
   разовой оплаты.

Для этапа 2 нужен отдельный раунд дизайна экранов кабинета (настройка петли/пакетов,
Telegram-подключение в интеграциях) — фронт для них не готов.

## 12. Нефункциональные требования

- **Таймзоны**: хранить всё в UTC, отображать в зоне владельца/клиента отдельно
  (см. `owner_timezone_at_booking` в §4). Расчёт слотов — всегда в зоне владельца
  расписания, конвертация в зону клиента — на фронте/в ответе API.
- **Конкурентность бронирования** — см. §8 п.2, обязательно.
- **Безопасность**: подпись вебхуков (когда подключится реальная ЮKassa), rate-limit
  на публичный `/book` и на запрос passwordless-кода, токены брони/сброса пароля — случайные,
  одноразовые, с TTL.
- **Локализация**: только русский в v1 (лендинг — язык переключатель убран, см. CHANGES.md).
- **Тариф/лимиты**: `free` — 1 формат, только Google Meet; `standard` — безлимит форматов +
  все три видео-интеграции + ручное подтверждение; `pro` — резерв полей под командные
  страницы/свой домен, бэкенд-логику для «Про» не проектируем в v1, кроме поля `plan`.

## 13. Открытые вопросы / решить с продактом до реализации

- Расписание (`availability_rules`) — общее на владельца или настраивается per формат?
  Макет `FormatEditor` показывает недельную сетку внутри редактора формата — уточнить,
  это предпросмотр общего расписания или отдельная настройка.
- CTA «Забронировать ранний доступ» на лендинге сейчас скроллит к общей форме email;
  нужен ли отдельный waitlist-эндпоинт для этих лидов — решить отдельно от этой спеки.
- Точный транзакционный email-провайдер и Telegram Bot API — выбор инфраструктуры,
  не блокирует модель данных выше.
